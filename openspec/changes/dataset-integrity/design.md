# Design

## Context

See `proposal.md` for scope and motivation, and DM-4 / CO-6 in
`../archive/2026-11-06-domain-driven-review/domain-review.md` for the binding
review findings.

Current state that shapes this design: `apps/api/src/datasource.ts` already
derives its local dataset-file types from the shared contract
(`Provider & { programs: Array<Program & { units: DatasetUnit[] }> }`),
while `tools/datagen/src/generate.ts` re-declares the full provider/program
field lists by hand. The API validates header provenance, duplicate unit ids,
fictional contacts, and `UnitCardSchema` conformance of available cards — but
nothing connects `unit.programId` to the enclosing program, and nothing checks
provider/program id uniqueness. Ownership in the frozen file is purely
structural nesting; `Program` carries no `providerId`.

## Goals / Non-Goals

**Goals:**

- Derive datagen record types from shared contracts (compile-time lockstep).
- Reject inconsistent dataset ownership and duplicate Provider/Program
  identities before projection.
- Preserve generated bytes and existing serving behavior for valid datasets.

**Non-Goals:**

- Shared-contract changes, dependencies, schema-version bumps, or ingestion
  redesign.
- Changes to filtering, availability, unknown-value semantics, or the
  memory-source contract.
- Reimplementation of the already-landed dataset seam rule.

## Decisions

These decisions bind implementation.

### 1. Derive datagen types locally through intersections

Use exported type aliases:

- `DatasetProgram = Program & { units: Unit[] }`
- `DatasetProvider = Provider & { programs: DatasetProgram[] }`

Import `Program` and `Provider` as types from shared. Keep the dataset
envelope and generator metadata local and unchanged. Construction sites must
satisfy these derived types without casts that bypass checking.

Rationale: required shared-field changes now reach generator construction
sites at compile time. Shared optionality remains intact — the shared package
already publishes `Static`-derived types with `Type.Optional` fields (e.g.
`applicationProcess`) that consumers construct and omit freely today, so
intersection with the derived `Program`/`Provider` preserves the same
optionality.

Alternatives:

- `Omit` adds no value because shared Program/Provider have no conflicting
  collection fields.
- Extending interfaces works but obscures the direct composition already used
  by the API.
- Publishing a shared dataset-file contract enlarges the API contract surface
  unnecessarily. Local generator/API envelopes may differ; shared record
  fields must not be redeclared.

### 2. Derive PolicyFields from Program

Replace its handwritten interface with `Pick<Program, ...>` over the existing
six policy keys. Preserve its export and key set.

Rationale: policy value types should evolve with Program too. Retaining a
handwritten subset leaves avoidable drift; extracting a new shared policy
abstraction exceeds scope.

### 3. Reject hierarchy violations before projection

Add one local `rejectDatasetHierarchyViolations` helper in
`apps/api/src/datasource.ts`. Call it after existing header checks and before
building any UnitCards.

Traverse the complete tree and enforce:

- Provider ids are unique across the dataset.
- Program ids are globally unique, including within one Provider.
- Every Unit's `programId` equals its enclosing Program's `id`.

Check empty Providers/Programs too. Reject the whole source; never repair
references, deduplicate records, skip offenders, or return partial inventory.

Use fail-fast diagnostics matching the existing lowercase dataset-error
style:

- `dataset carries duplicate provider ids: <id>`
- `dataset carries duplicate program ids: <id>`
- `dataset carries unit <unitId> with programId <actual> but enclosing
  program id <expected>`

Report the first encountered violation in file traversal order. No diagnostic
includes contact data or whole records.

Structural nesting supplies each Program's Provider and each Unit's enclosing
Program. Unique Provider/Program identities, matching Unit references, and
existing dataset-wide Unit-id uniqueness therefore enforce the existing
exactly-one ownership requirement. No `providerId` field is needed.

Alternative: checking projected cards loses empty-node coverage and obscures
structural ownership. Broadening the memory-source interface or adding a
general validation framework is unnecessary.

### 4. Check every Unit regardless of availability

Run hierarchy checks before availability filtering. Keep existing
duplicate-Unit-id, fictional-contact, header, and available-only
`Value.Check(UnitCardSchema, card)` gates unchanged.

Rationale: hidden records still belong to the loaded dataset. Filtering must
not conceal ownership corruption that could become visible after an
availability change.

This is targeted integrity enforcement, not complete runtime schema
validation of every hidden record. Arbitrarily malformed JSON remains outside
this change's expanded guarantees.

### 5. Add an enforcement requirement without rewriting the hierarchy requirement

Add "Dataset hierarchy integrity at the serving boundary" to
`housing-inventory`. Leave "Three-layer inventory hierarchy" unchanged.

Three rejection scenarios cover mismatched Unit ownership, duplicate Program
ids, and duplicate Provider ids. Existing hierarchy-serving coverage already
describes successful resolution; retain a valid-file API regression test
without duplicating that spec scenario.

### 6. Extend generator structural checks

Extend the existing structural-invariants helper to assert Provider-id
uniqueness and global Program-id uniqueness. Retain its Unit-to-Program
assertion.

Rationale: this catches generator identity regressions at generation tests
rather than waiting for API boot. Reuse existing collections where practical;
no new fixture framework.

Generator runtime construction, random draws, insertion order, and
serialization remain unchanged. The source type refactor is type-only;
`data/` must remain byte-identical.

### 7. Keep boundaries and verification explicit

Production work stays in datagen and the API DataSource; shared schemas,
routes, and architecture rules remain unchanged. Tests use shared fluent
builders from the testing subpath and existing scratch-dataset helpers.

No OpenSpec tracking references may enter production comments or human-facing
docs outside `openspec/`. Implementers never commit. Human approval of these
planning artifacts precedes implementation; code and security review precede
orchestrator commits. No UI verification is required.

## Risks / Trade-offs

- [Previously tolerated corruption now prevents startup] → Reject
  deliberately; diagnostics identify offending identities. Never weaken
  guards to admit a corrupt file.
- [TypeScript derivation is mistaken for runtime validation] → Retain
  existing runtime gates and add explicit hierarchy checks.
- [Local file envelopes remain duplicated] → Derive all shared record fields;
  defer envelope consolidation until a real cross-workspace contract is
  needed.
- [Generator changes accidentally alter frozen output] → Existing
  byte-identity tests plus regeneration and an empty `data/` diff are
  mandatory.
- [Available-only tests miss hidden corruption] → Exercise mismatched
  ownership across available, not-available, and unverified-availability
  records.

## Migration Plan

1. Obtain human approval of design, delta, and tasks; remove `skip_specs`
   when the delta is installed.
2. Derive datagen types and extend structural tests. Prove byte identity.
3. Add hierarchy rejection tests and the pre-projection guard. Preserve
   valid-file serving.
4. Run full gates and regenerate data; retain review evidence before
   orchestrator commit.

No data migration or schema-version change. Valid datasets serve unchanged.
Rollback is a revert of code/tests and corresponding spec changes; never
hand-edit generated data.
